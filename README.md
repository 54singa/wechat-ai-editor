# wechat-ai-editor

一个为「AI热点」公众号沉淀的个人创作 Skill。它把过往写稿过程中反复确认过的选题判断、案例组织、公众号叙事、人味表达、局部改稿和标题偏好整理成可复用的工作方式。

这个 Skill 主要回答五类问题：

- 这条 AI 新闻值不值得写，应该从哪里切入？
- 商稿或自选题应该设计什么案例，怎样让普通读者看懂？
- 已有材料怎样写成公众号文章，而不是产品说明书或技术报告？
- 一段话为什么“太 AI”“太硬”“太广告”，应该怎么改？
- 标题如何兼顾点击动机、正文兑现和产品必带词？

它适用于商稿、自选实测、观点资讯、工具教程和轻随笔。完整写稿或大幅润色时，建议同时调用 `human-writing`；前者负责「AI热点」的账号定位、选题、案例和编辑偏好，后者负责通用中文表达、节奏和去模型腔。

## 安装

仓库是一个完整的 Skill 目录。将它克隆到 Codex 的 skills 目录即可：

```bash
git clone https://github.com/54singa/wechat-ai-editor.git ~/.codex/skills/wechat-ai-editor
```

这是私有仓库，命令行需要已经登录有权限的 GitHub 账号。也可以下载仓库后，将整个目录复制到：

```text
~/.codex/skills/wechat-ai-editor/
```

安装后应至少保留下面的结构：

```text
wechat-ai-editor/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── references/
    ├── editorial-profile.md
    ├── topic-and-cases.md
    ├── drafting-and-revision.md
    ├── titles-and-hooks.md
    ├── voice-examples.md
    ├── publishing.md
    └── evidence-index.md
```

如果同名 Skill 已存在，更新时进入目录拉取最新版本：

```bash
cd ~/.codex/skills/wechat-ai-editor
git pull
```

## 怎么调用

在任务中直接点名 `wechat-ai-editor`，并说明你当前需要的交付物。无需每次把整篇文章的所有信息重新整理成表格；有 Brief、大纲、截图、实测结果或现有稿件时，直接一起提供。

最简单的调用方式：

```text
请使用 wechat-ai-editor，帮我判断这个热点适不适合公众号，并给 3 个切入方向。
```

```text
请使用 wechat-ai-editor，根据这份 Brief 和实测材料写公众号初稿。
正文写作同时配合 human-writing，让表达自然一点。
```

```text
请使用 wechat-ai-editor 改下面这一段。逻辑不变，只解决太硬、太像产品说明的问题。
```

```text
请使用 wechat-ai-editor，根据全文给 15 个公众号标题。
必须带产品名，分成结果型、好奇型和亲测判断型，不要只换同义词。
```

Skill 会先判断本轮属于选题、案例、写稿、改稿、标题还是发布检查，再读取对应参考文件。只改一句时不会把整篇重写；只讨论方向时也不会擅自扩成完整稿件。

## 推荐工作流

### 1. 从热点到选题

先给新闻、链接、截图或一句背景，再说明你需要快速判断还是完整策划。

推荐提示词：

```text
请使用 wechat-ai-editor 看这个热点。

我的目标读者：对 AI 感兴趣的普通互联网从业者。
我想知道：
1. 它为什么值得写；
2. 普通读者真正关心的是什么；
3. 能不能设计一个可展示结果的实测；
4. 给 3 个不同切口，并标一个首选。

新闻/材料：……
```

预期得到的不是泛泛的“AI 提升效率”，而是类似下面这种方案：

> **首选：让 AI 接手一次真实的临时改稿**  
> 从“功能很多，但能不能救急”切入。准备一份结构混乱的会议记录，让工具完成提炼、改写和版式整理，展示初版、人工追问和最终交付。读者能看到它省掉了哪一步，也能看到哪些地方仍要自己处理。

### 2. 设计实测案例

案例应服务文章的核心问题，不为凑数量重复展示同一种能力。把现有条件和不能做的事说清楚，Skill 会优先设计最小可执行验证。

```text
请使用 wechat-ai-editor 设计这篇稿的实测案例。

产品：……
核心卖点：……
我能使用的材料/工具：……
时间限制：……
希望最终展示：截图 / 视频 / 成品链接
不要做：复杂跑分、纯技术参数比较

请给一个主案例和两个简短补充案例，并说明各自验证什么。
```

如果已经有真实结果，应直接提供。Skill 会区分：

- Brief 或提示词里计划实现的能力；
- 初版真正产出的内容；
- 修改后得到的结果；
- 用户自己的体验和判断；
- 官方或第三方演示。

这能避免把“准备做”写成“已经做成”，也避免根据大纲补造截图里没有出现的功能。

### 3. 写公众号初稿

完整写稿时，建议同时调用 `human-writing`。

```text
请使用 wechat-ai-editor，并配合 human-writing 写一篇公众号初稿。

文章类型：自选实测 / 商稿 / 观点资讯 / 随笔
目标读者：……
核心问题：……
必须写到：……
不要写：……
希望篇幅：……
语气：自然、随性，可以有一点调侃，但不要每段都玩梗

材料：
1. ……
2. ……
3. ……

先给正文，不附写作原理。无法从材料确认的地方明确留出素材位。
```

两套 Skill 的推荐分工是：

| Skill | 主要负责 |
|---|---|
| `wechat-ai-editor` | 账号读者、选题价值、案例结构、事实边界、公众号节奏、用户历史修改偏好、标题 |
| `human-writing` | 通用中文自然度、句子节奏、去套话、减少模型腔 |

推荐顺序是先由 `wechat-ai-editor` 确定文章为什么写、写什么、材料能证明什么，再让两套规则共同参与正文表达。最后仍回到 `wechat-ai-editor` 检查案例主次、事实状态和标题兑现。

如果 `human-writing` 当前不可用，`wechat-ai-editor` 仍能独立完成写稿；它不会假装调用成功，也不会自动安装另一个 Skill。

### 4. 逐段写作或续写

你可以只给当前段落和前后作用：

```text
请使用 wechat-ai-editor 续写案例二，只写 3—4 段。

上文已经讲了：……
这一段要完成：解释为什么换了第二个工具，并写出结果不如预期的感受。
必须保留：……
不要重复：产品基础功能、案例一的结论。
```

这种用法适合边看素材边写。Skill 会把交付控制在当前段落，不自动补完整篇文章。

### 5. 局部改稿

指出问题类型和允许改动的范围，效果最好。

```text
请使用 wechat-ai-editor 改这两段：

问题：描述图片细节太多，人味和判断太少。
要求：逻辑、事实和段落顺序不变；保留第二段最后一句；压缩约 20%。
只返回修改后的段落。

原文：……
```

```text
请使用 wechat-ai-editor 给这句话 5 个改法。
现在的问题是调侃写得像真实商业计划。
不要改前后文，也不要增加不存在的经历。

原句：……
```

Skill 会优先判断你改的是逻辑、语言、篇幅还是语气。像“稍作充实”“逻辑不变”“只改这句”“先聊思路”这类范围要求会被当作明确边界。

### 6. 标题与开头

标题需要基于全文，而不是只抓开头几个关键词。

```text
请使用 wechat-ai-editor 阅读全文后给标题方案。

必须出现：产品名 A、产品名 B
想突出：一手实测和价格反差
不要使用：颠覆、炸裂、重新定义
数量：18 个

请按“具体结果、读者收益、反差好奇、亲测判断”分组；
每组角度要有实质差异，最后选 3 个首选并说明理由。

全文：……
```

标题的核心标准是：读者看完标题产生的期待，正文确实能够兑现。没有实际数据时，Skill 只判断吸引力，不会把候选标题称为“验证过的爆款”。

开头也可以单独处理：

```text
请使用 wechat-ai-editor 重写这个开头，给 3 个方向：
1. 从失败结果切入；
2. 从普通读者疑问切入；
3. 从一次具体尝试切入。

不要增加感叹号，不编大众都在抵制，也不要提前剧透全部结论。
原文：……
```

### 7. 发布前检查

```text
请使用 wechat-ai-editor 做发布前检查。

重点核对：
- 标题是否被正文兑现；
- 产品名、版本、价格和权益是否与本次材料一致；
- 有没有把计划写成亲测；
- 图片与相邻段落是否对应；
- 哪些段落重复或太长；
- 商稿 Brief 的必写信息是否自然保留。

先列必须修改的问题，再给可直接替换的文字。
```

发布检查不会自动发布文章、发送消息或创建定时任务。

## 完整示例

下面是一个虚构示例，用来展示 Skill 的协作方式，不代表真实产品事实或历史定稿。

### 输入

```text
请使用 wechat-ai-editor，并配合 human-writing。

我想写一篇“AI 做演示文稿”的公众号实测。
手里有三组材料：
1. 第一次输入一句话，结构完整，但内容很空；
2. 第二次补充公司背景和听众，内容好了，但图表数据是占位符；
3. 我手动换掉数据后，最终版本可以拿去开会。

先给我：
- 一个文章主线；
- 开头 2 版；
- 正文结构；
- 12 个标题。

读者不是设计师，别写成软件评测。语气自然，可以吐槽，但不能说它已经完全替我做完工作。
```

### 合理的主线

> 这次不是比较模板数量，而是看 AI 能不能把一句模糊需求推进到一份真正可以开会用的演示文稿。第一次生成证明它会搭架子，第二次追问让内容接近实际需求，最后替换数据则说明人工仍然要为事实负责。

### 开头示例

版本一，从结果反差切入：

> 第一次看到它交来的 PPT，我差点以为今晚能提前下班。标题、目录、配图一个不少，翻到数据页才发现，最像那么回事的几张图，恰好都不能直接用。于是这次实测真正的问题也来了：AI 会做 PPT，和它能做出一份拿去开会的 PPT，中间到底还差几步？

版本二，从普通读者需求切入：

> 大多数人做 PPT，卡住的往往不是不会调字体，而是不知道这一页到底该说什么。我把一句相当含糊的需求交给 AI，想看看它能不能从“帮我做个汇报”，一路追到一份真的能在会议室打开的文件。

### 正文结构示例

1. **一句话先搭出架子**：展示首版结果，肯定结构速度，同时指出内容空泛。
2. **信息给够以后，它开始像个同事**：写第二轮补充背景和听众后的变化，挑最能支持判断的细节。
3. **最像成品的地方，反而最需要小心**：解释占位数据问题，区分视觉完成度和事实可用性。
4. **最后这一步仍然得自己来**：写人工换数据后的交付，落到真实省时环节和仍需负责的部分。
5. **结尾**：回到“能不能拿去开会”，给出有范围的个人判断，不重列全部功能。

### 标题方向示例

- 一句话让 AI 做 PPT，真正拿去开会前还差这几步
- 我把一份模糊需求交给 AI，最后真的做成了汇报
- AI 做的 PPT 第一眼很完整，最像成品的地方却要重做
- 测完 AI PPT，我发现它最省时间的不是排版
- 从一句话到会议室：我和 AI 来回改了三版 PPT

这些标题对应不同阅读动机。实际使用时，Skill 会根据全文、必带词和商稿要求继续扩展，而不是把同一句话换几个动词。

## “人味”在这个 Skill 里是什么意思

这里的人味不是固定加入“说实话”“谁懂”“有点意思”，也不是每段安排一个梗。它来自材料中的具体反应、选择和判断：

- 看到什么中间结果时产生了期待；
- 哪个细节让期待落空；
- 为什么改提示、换工具或放弃某个方案；
- 做完后愿不愿意继续用，用在什么范围；
- 哪个不足真正影响交付。

例如：

```text
模型给出了完整的页面结构，效果令人惊喜，但仍有进一步优化空间。
```

这句话很平衡，却没有提供新信息。基于真实材料，可以改成：

```text
首页出来时我确实松了口气，至少不用再对着空白画布发呆。可翻到数据页，几张看起来最专业的图全是占位内容——架子它搭得很快，数字这件事还是得我自己负责。
```

后一句之所以更自然，是因为情绪贴着“首页”和“占位数据”发生。若材料里没有这些结果，就不能为了人味照搬。

## 使用边界

- 不把提示词、大纲或 Brief 当成已经发生的实测结果。
- 不编造作者经历、对白、耗时、个人偏好或成功效果。
- 不把第三方演示写成“我亲测”。
- 不机械套用历史文章的产品名、价格、案例数量和标题必带词。
- 不因追求简短删掉陌生工具所需的一句铺垫。
- 不因追求人味堆口头禅、粗口、感叹号和夸张反问。
- 不在用户只要一句修改时顺手重写整篇。
- 不自动发布、发消息或替用户执行外部操作。

产品版本、价格、权益、排行榜和热点热度会变化。使用这些信息时，应以本次材料或重新核验的来源为准。

## 维护方式

这个 Skill 应随着明确的新反馈更新，但不把一次普通写稿中的默认选择自动升级成永久规则。新增经验时建议记录：

1. 当时的原句或任务背景；
2. 用户明确指出的问题；
3. 后续修正方向；
4. 这段内容是用户要求、认可文本、候选方案还是编辑推断；
5. 它适用于哪类文章，不能推广到哪些场景。

这样可以让 Skill 越来越懂账号，同时避免把一篇文章的临时要求错误地套到后续所有创作中。
